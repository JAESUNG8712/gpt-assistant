## 재현한 문제 및 구현

알림 작업 A의 임대가 만료되고 B가 같은 건을 가져갔어도, `_outboxFinish()`는 ID만으로 갱신했다. A의 늦은 실패가 B의 `sending` 상태를 `pending`으로 바꾸는 것을 실제 JSON 저장 함수 회귀 테스트로 재현했다. 늦은 성공 또한 같은 갱신 경로를 사용했다.

- enqueue/claim 시 새 `claimToken`을 발급한다.
- 완료·실패·취소 기록은 ID + 회사 + sending 상태 + 소유 토큰 + 유효 임대가 모두 일치할 때만 갱신한다. PostgreSQL은 단일 조건부 UPDATE, JSON은 기존 저장 잠금 안에서 검사한다.
- 발송 직전 같은 조건으로 임대를 갱신한다. 만료되었거나 다른 작업자로 넘어간 건을 새 HTTP 요청으로 보내지 않는다.
- 유효 임대를 잃은 결과는 `superseded`로 내부 처리하고 발송 성공/실패 로그나 성공 건수에 추가하지 않는다.
- 워커는 최대 20건을 한꺼번에 점유하지 않고 한 건씩 점유→처리한다. 한 주기의 최대 작업량 20건은 유지한다.
- 빈 전송 로그를 저장하지 않아 불필요한 상태 저장을 줄인다.
- 작업 토큰은 관리자 목록 API에도 노출하지 않는다.

이것은 **저장 상태 덮어쓰기 방지**이며 외부 수신 시스템에 정확히 한 번 전달한다는 보장은 아니다. HTTP 성공 직후 서버 종료, 수신 성공과 응답 유실 등의 재전송 가능성은 남는다.

## 스키마·배포 주의사항

`schema.sql`에 `ALTER TABLE webhook_outbox ADD COLUMN IF NOT EXISTS claim_token TEXT`만 추가한다. 기존 행/업무 자료 삭제나 전체 백필은 없다. 기존 pending 또는 만료된 sending 건은 새 워커가 점유할 때 토큰을 얻는다.

**이번 작업에서 운영에 적용하지 않는다.** 배포 승인 시에는 백업 후 별도 검증 환경에서 스키마와 워커를 확인한다. 구버전 워커는 토큰을 검사하지 않으므로 신·구버전 워커의 혼재 상태에서는 안전을 보장하지 못한다. 기존 워커를 종료한 뒤 새 코드만 실행하는 순서를 사용한다. 이미 전송 중인 외부 HTTP 요청은 취소/회수되었다고 가정하지 않는다.

## 검증

- 수정 전 JSON 저장 함수 재현: 늦은 실패가 새 소유자의 상태를 변경하여 테스트 실패.
- 수정 후 소유권·만료·회사 격리·중복 콜백·최대 작업량 회귀 테스트 추가.
- PostgreSQL 임시 DB 회귀: 실제 HTTP 응답을 보류한 동안 DB에서 소유권을 넘긴 뒤, 늦은 HTTP 200/500 모두 새 상태·시도 횟수·로그를 변경하지 않는지 검사한다.
- 실제 HTTP 전송/SSRF 차단/재시도/메뉴 권한/복구 API 기존 회귀도 함께 실행한다.
- 로컬 문법 검사 통과. 통합 집중 회귀 28건 통과 후 최대 작업량/API 토큰 비노출 검증을 추가한 최종 outbox 회귀 8건도 통과했다(중복 실행 수를 합산하지 않는다).
- 최종 PostgreSQL/E2E 결과는 이 문서가 포함된 브랜치의 최신 커밋 CI에서 확인한다. 이전 커밋의 성공을 대신 사용하지 않는다.
- 첫 CI(`41368445341`)는 539건 중 538건 통과, 기존 펄스 설문의 고정 종료일(2026-10-31) 때문에 1건 실패했다. 로컬에서도 동일 실패를 재현했다. 서버의 기간 제한은 유지하고 테스트를 실행일 상대 날짜로 변경했으며, 시작 전·종료 후 저장 차단과 정상 응답 보존을 추가 검증한다. 이 실패 때문에 첫 CI의 PostgreSQL 전용/E2E 단계는 실행되지 않았다.

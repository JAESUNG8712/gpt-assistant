# HR 기능 연계·권한·동시 저장 종합 점검

기준: `hr-production`에서 파생된 `codex/modal-lock-qa`, PR #157.
HR 앱만 대상으로 한다. 별도 AI 어시스턴트 앱은 포함하지 않는다.
운영 DB의 직원·급여·교육 원본을 이전하거나 삭제하는 작업은 수행하지 않았다.

## 확인된 결함과 반영 내용

| 분야 | 확인된 문제 | 반영한 처리 |
| --- | --- | --- |
| 편집 충돌 | 중첩 확인창만 닫아도 부모 편집 잠금과 자동 초안이 종료됨 | 마지막 편집창을 닫을 때만 해제 |
| 경비·회계 연결 | 전표 확정 후 경비 원장에 임시 번호가 남음 | 확정 번호 동기화. PostgreSQL은 전표와 경비 갱신을 같은 트랜잭션에서 처리 |
| 교육 조회 권한 | 일반 직원에게 관리자 메뉴 설정이 읽기·쓰기의 우회 경로가 됨 | 역할과 실제 사용할 수 있는 메뉴를 함께 판정. 관리 메뉴가 꺼진 관리자의 타인 신청 관리도 차단 |
| 교육 정원 | 개인정보 필터로 줄어든 클라이언트 신청 목록으로 정원을 계산함 | 서버 원장의 집계 건수만 제공. 회사별 저장 잠금 안에서 최종 정원을 확인하고 초과 신청은 대기로 변경 |
| 교육 무결성 | 중복 신청, 없는 과정/직원, 마감 과정 신청, 과정·수료일 변경을 서버에서 충분히 검증하지 않음 | 저장본과 신규 변경을 대조. 본인 변경은 취소·설문 범위로 제한하고 기존 이력은 보존 |
| 교육 날짜 | 날짜 형식만 맞는 2월 30일 등도 통과 가능 | 실제 달력 날짜 검증 |
| 자료 통합 UI | 두 교육 원장이 분리되어 있고 통합 목록은 최근 25건만 볼 수 있음 | 출처 표시, 한글 상태, 과정·직원·사번·부서·상태 검색, 페이지 이동, 조회 결과 CSV |
| 웹훅 알림 | 임의 문구 전달, 저장 전 발송, 중복 발송 및 권한 철회 후 발송 위험 | 저장된 업무 기록과 실행 주체 검증, 회사 기능·개인 메뉴 확인, 저장 이후 발송, 이벤트 중복 차단 |
| 웹훅 테스트 | 브라우저 no-cors 요청이 실제 HTTP 실패도 성공처럼 표시함 | 서버에 저장된 대상만 호출. 내부 주소/리다이렉트 차단과 실제 HTTP 결과 확인. 관리자·메뉴 권한 및 호출 제한 적용 |
| 알림 재시도 | 배열 순회 중 삭제로 일부 항목을 건너뛰고 재시도 간격을 건너뛸 수 있음 | 순회 복사본·안전한 제거·재시도 시각·응답 시점 세션 확인 |
| 비동기 오류 | Express 4에서 중첩 배열에 등록한 async 핸들러의 거부가 오류 처리기로 전달되지 않음 | 재귀 래핑으로 요청 오류 응답 및 서버 생존 보장 |

## 통합 원칙

- 교육 배정·결재 원장과 직접 신청·설문 원장은 조회 화면에서 연결한다. 같은 과정명만으로 동일한 교육이라고 판단하지 않는다.
- 동일 과정명으로 비용을 자동 합산하거나 중복 기록을 삭제하지 않는다. 향후 공통 과정 식별자를 도입할 때 관리자 확인을 거친 매핑을 사용한다.
- 직원별 교육 응답은 본인 기록으로 제한하고, 정원은 개인 정보가 없는 집계 건수로 제공한다.
- JSON/PostgreSQL이 같은 교육 검증 함수를 사용한다. PostgreSQL은 요청 내에서 검증 자료를 한 번 읽고, 수락한 레코드를 기준에 누적한다.
- 웹훅 테스트·자동 발송은 같은 목적지 검증·전송·기록 함수를 사용한다. 연결 오류에 비밀 URL이 포함되지 않도록 일반화한다.
- 원격 운영 브랜치와 비교 후 기존 PR에 변경을 모은다. 강제 푸시 또는 별도 앱 브랜치 병합은 하지 않는다.

## 검증 범위와 한계

- 전체 기본 회귀: 인증·메뉴/모듈 권한, 평가 단계, 급여/복지 연결, 전표·예산·ERP/PMS·채용, 저장 충돌·복원, 교육·그룹웨어 관련 등록된 테스트.
- 추가 API 검증: 동시 정원 신청, 중복/마감/없는 참조 거부, 관리자 메뉴 제한, 신청 원본 보존, 실제 웹훅 HTTP 실패/SSRF 차단, 중첩 async 오류.
- UI 회귀: 통합 교육 이력 페이지 이동·출처 검색·한글 상태와 CSV 결과 일치. 기존 모달 잠금·경비 전표 표시 테스트도 유지.
- 로컬은 격리된 임시 JSON 파일을 사용한다. PostgreSQL은 GitHub CI의 임시 DB에서 실행한다. 운영 DB로 테스트하지 않는다.
- 이 Windows 환경의 Playwright는 `spawn EPERM`으로 시작하지 못한다. 브라우저 통과 여부는 해당 커밋의 GitHub CI 결과로 판단한다.
- 테스트 통과는 모든 운영 화면·실제 자료가 무결하다는 증명이 아니다. 최종 테스트 수와 CI 상태는 PR/작업 결과에 기록한다.

## 남은 개선 과제 — 우선순위 및 완료 기준

아래는 이번에 구현 완료한 기능으로 표기하지 않는다.

1. **P1: 저장과 알림의 영속 전송 대기함 통합.** 현재 알림 큐는 브라우저 메모리이고 서버는 발송 전 중복 예약을 한다. 저장 후 브라우저 종료 또는 예약 후 프로세스 종료 시 알림이 누락될 수 있다. 업무 저장 트랜잭션에 이벤트를 기록하고, 목적지별 전송 상태·재시도·실패 목록을 가진 작업자로 분리해야 한다. 외부 수신 서비스의 중복 처리 지원이 없다면 정확히 한 번의 전달은 보장할 수 없으므로 메시지 이벤트 ID를 함께 전달한다. 완료 기준은 저장 직후 종료·재기동·여러 목적지 중 일부 실패를 재현한 검증이다.
2. **P1: 오래된 클라이언트의 수정 충돌 우회 종료.** 일부 회계 수정 경로는 호환성을 위해 최신 수정시각 없이도 쓰기를 허용한다(`test/api-accounting-cas.test.js`의 레거시 호환 테스트). 화면별 전송 확인 후 revision 필수화와 409 충돌 복구 UX를 적용해야 한다. 완료 기준은 두 탭에서 같은 계정/거래처를 수정해도 앞선 변경이 유실되지 않는 것이다.
3. **P2: 전송 이력 보관 정책.** 화면의 50건 제한은 DB/파일 저장량 제한이 아니다. 보관 기간·내보내기·삭제 대상을 명시한 관리 기능이 필요하다. 기존 이력을 일괄 삭제하지 않고, 미리보기와 보관 정책 설정 후 적용한다.
4. **P2: 공통 교육 과정 식별자와 연결 검토 화면.** 읽기 통합 이후 관리자가 두 출처의 동일 과정을 선택해 연결하는 단계가 필요하다. 원본 ID·이수/설문·승인비용·정산은 출처별로 보존한다. 연결 전후 인원·이수 건수·비용 대조 및 연결 취소가 완료 기준이다.
5. **P2: 권한 정의와 업무 모듈 분리.** 서버와 화면의 메뉴 정의가 분산되고 `server.js`/`public/index.html`에 여러 도메인이 모여 있다. 이번 교육 검증처럼 독립 함수를 우선 추출하고, 역할×메뉴×행 범위를 공통 정책으로 표현한다. 일괄 재작성보다 기능별 회귀 테스트를 유지하며 이동한다.
6. **P2: 실제 업무 UI 시나리오 확대.** 이번 교육 화면 외에도 평가자 선정→평가 확정→보상·급여 반영, 경비→전표 확정, 권한 변경→열려 있는 탭 재동기화를 관리자/일반 직원·모바일 조건에서 연속 검증해야 한다. 각 메뉴가 열린다는 스모크 테스트와 구분해 업무 결과의 저장·재조회까지 확인한다.

신규 기능 추가보다 1~2번의 장애·충돌 복구를 우선한다. 3~6번은 저장소 정리, 원장 연결, 모듈 분리, 업무별 UI 검증 순으로 진행한다.

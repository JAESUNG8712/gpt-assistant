# ERP·급여 연계 무결성 점검

기준 브랜치 `hr-production`, 기준 커밋 `733d26e`. 별도 AI 앱은 제외했다.
운영 DB의 자료 정리·백필·삭제는 수행하지 않는다.

## 수정 범위

| 문제 | 조치 |
| --- | --- |
| 견적 확정/반려, 발주 취소/삭제, 구매요청 승인/반려/삭제의 조회와 변경 사이 경쟁 | 공통 `_changeErpDocument`에서 PostgreSQL 행 잠금과 회사 조건을 같은 트랜잭션에 적용 |
| 구매요청에서 생성한 발주서 삭제 시 원래 요청의 연결이 끊김 | 연결된 발주서는 삭제 대신 취소하도록 409 응답, 연결 이력 유지 |
| JSON 단일 문서 변경과 발주 전환의 저장 실패 후 메모리 선반영 | 복제본 저장 성공 후 메모리 교체 |
| JSON 입출고에서 ERP·회계 두 파일 중 일부만 저장 | 이전 파일 내용을 담은 비공개 복구 기록으로 실패/재시작 시 두 파일 복구, 복구 전 요청은 503 |
| 장기근속 포상의 임의 식별 키를 이용한 반복 지급 | 직원·근속연수별 정규 키 검증 및 기존 저장 잠금 아래 중복 검사 |
| 포상·급여 변경이 거절되어도 인사 이력만 저장 | 연결 변경의 의도를 저장 전 상태와 대조하고 커밋 직전 검증, 불일치 시 전체 저장 거절 |
| 저장 결과 확인 전 포상 반영 완료 표시 | 명시적 저장 결과를 기다린 뒤 성공 안내, 실패 시 최신 상태 재조회 |

## 통합과 호환성

- 동일한 문서 상태 변경 로직을 공통 함수로 통합했다. 입출고와 발주 전환은 여러 자료를 함께 변경하므로 기존의 넓은 트랜잭션을 유지한다.
- PostgreSQL 문서 변경은 `company_id`가 현재 회사와 일치해야 한다. 회사 미지정(NULL) 문서는 자동 귀속시키지 않는다. 기존 `audit:company-scope`의 읽기 전용 결과를 확인한 후 별도 백필 절차로 처리한다.
- JSON 저장 모드는 기존과 같이 단일 프로세스 전용이다. 복구 기록은 ERP·회계 두 파일의 프로세스 중단 복구를 위한 것이며 DB 백업이나 다중 프로세스 잠금을 대체하지 않는다.
- 파일 기록 자체가 읽히지 않거나 복구가 실패하면 빈 자료로 덮어쓰지 않고 요청/기동을 차단한다.
- 급여의 기존 일반 부분 저장 계약은 유지하되, 포상과 인사 이력을 함께 변경하는 업무는 부분 성공으로 처리하지 않는다. 모든 HR 업무를 전용 명령 API로 전환한 것은 아니다.

## 회귀 검증 범위

- JSON 견적 확정/반려 및 발송/삭제 동시 요청
- PostgreSQL 두 서버의 견적 확정/반려, 발주 취소/입고, 구매요청 승인/반려/삭제 경합
- 타 회사·회사 미지정 문서 변경 거절
- 전환 발주 연결 보존, 파일 저장 실패 시 메모리 불변과 재시도
- 두 파일 중 두 번째 쓰기 실패, 기록을 남긴 중단 상태의 복구, 복구 실패 시 후속 쓰기 차단
- 포상 키 위조, 재전송, 배치·동시 저장 중복, 포상·명세서·직원 이력 연결 저장

로컬 Windows에서 일부 API 테스트는 서버 프로세스 시작 지연으로 assertion 실행 전에 제한시간을 넘겼다. 이 실패를 기능 통과로 계산하지 않는다. 최종 PostgreSQL·브라우저 검증은 GitHub Actions의 임시 DB 및 Chromium 결과를 기준으로 별도 기록한다.

## 추가 개선 후보

1. 포상·급여 계산은 장기적으로 서버 전용 적용/취소 API로 옮겨 계산 규칙과 변경 권한을 한곳에서 관리한다.
2. ERP 마스터/일반 생성 경로의 JSON 저장에도 복제본 저장 방식을 확대한다. 이번 변경이 모든 JSON 쓰기 경로를 바꾼 것은 아니다.
3. 회사 미지정 자료의 읽기 호환 정책과 백필 완료 기준을 운영 문서에 명시한다. 실제 DB 확인 없이 미지정 자료가 없다고 단정하지 않는다.

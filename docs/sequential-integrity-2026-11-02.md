# 순차 개선: 저장·알림, 복구, 권한, 화면 검증

## 적용 범위

HR/ERP 개발 브랜치 `codex/post-merge-integrity-qa`. 운영 브랜치 병합, Render 배포, 운영 DB 변경은 수행하지 않는다. 별도 AI 앱은 대상이 아니다.

## 1. 업무 저장과 알림 등록

- `/save`에서 권한·상태 검증을 통과한 **실제 저장 결과**를 비교한다. 새 공지, 결재 상신, 휴가 상신, 최종 승인/반려 전환만 서버가 알림으로 만든다.
- PostgreSQL은 업무 변경, outbox INSERT, 수정·삭제 이력 INSERT를 같은 트랜잭션으로 처리한다. 알림/이력 기록 실패 시 업무 변경도 롤백한다. 커밋 전에는 메모리 버전도 올리지 않는다.
- JSON은 업무 파일에 비공개 `_pendingSaveEffects` 저널을 함께 원자적으로 저장한다. 워커/이력 조회에서 outbox와 이력 파일로 재반영하고, 모두 성공해야 저널을 지운다. 이벤트 키와 고정 이력 ID로 재실행 중복을 막는다.
- JSON 저널은 `/data`·저장 응답에서 제외하고, 클라이언트가 넣거나 삭제하려는 값도 무시한다. 손상된 보조 파일을 빈 파일로 덮어쓰지 않는다.
- 기존 브라우저 dispatch는 호환용으로 유지한다. 이미 서버가 등록한 알림을 다시 만들지 않고, 최초 대기 건만 점유해 즉시 처리할 수 있다.
- 변경 없는 전체 상태 재저장, 일반 제목 수정, 복구 작업에는 신규 알림을 만들지 않는다. 과거 자료 전체를 소급 발송하지 않는다.

## 2. 복구 미리보기와 충돌 방지

- `GET /api/record-revisions/:id/preview`: 업무 권한과 보관본 완전성을 검사하고, 영향 1건·필드·제목·변경 필드 목록·대상 비교 토큰을 반환한다. 원본 비밀값/전체 snapshot은 반환하지 않는다.
- 복구 요청에는 미리보기의 `expectedToken`이 필요하다(없으면 428). 저장 잠금 안에서 현재 레코드와 삭제 표식을 다시 비교한다. 확인 이후 변경되면 409로 중단한다.
- 복구로 바뀌는 현재 내용의 이력도 PostgreSQL 동일 트랜잭션/JSON 저널에 보관한다. 확정 급여 등 기존 보호 규칙은 유지한다.
- 화면에서 영향 범위를 확인하고 복구하며, 충돌하면 최신 내용 재확인을 안내한다. 구버전 클라이언트의 직접 복구는 428이므로 배포 후 새로고침이 필요하다.

## 3. 알림 요청자 권한 철회

- outbox에 `actor_id`, `record_id`를 기록한다. 실제 발송 직전에 현재 회사 직원 원본의 존재·활성 상태·이벤트 메뉴 권한을 다시 확인한다.
- 퇴사/삭제/메뉴 철회는 취소 처리한다. DB 조회 장애를 권한 있음으로 처리하지 않고 재시도한다. 관리자 수동 재시도에도 같은 검사를 적용한다.
- 요청자 정보 없는 구버전 대기 건은 추정하여 발송하지 않고 취소한다. 배포 전 관리자가 발송 대기함을 확인해야 한다.
- 이미 외부로 전달된 HTTP 요청을 취소·회수하는 기능은 아니다. 수신 후 응답 유실에 따른 중복 전달 가능성도 남으므로 수신측 멱등 처리가 필요하다.

## 4. 검증 범위

- JSON/API: 저장 직후 SIGKILL → 동일 파일로 재시작 → 브라우저 dispatch 없이 전달/이력 복구. 보조 이력 파일 손상 시 반복 오류와 저널 보존, 복구 후 중복 없음.
- 복구/API: 미리보기 없는 요청 거절, 확인 후 동료 수정 시 409, 최신 자료 보존, 새 미리보기로 정상 복구, 기존 비밀번호/확정 급여/메뉴 보호 유지.
- 권한/API: 알림 접수 후 요청자의 메뉴 철회 → 관리자 재시도 → 외부 발송 0건.
- PostgreSQL 임시 DB: outbox/이력 INSERT 오류를 트리거로 주입해 업무 변경 롤백 검증. 기존 회사 격리·늦은 응답·회사/모듈 정지 회귀 유지.
- 브라우저: 실제 저장 API로 만든 이력의 영향 확인창을 연 상태에서 동시 수정 → 최신 자료 보존 → 다시 확인 후 복구.
- 전체 기존 API/E2E는 최신 커밋의 CI 결과로 판정한다. 테스트 추가 자체와 실행 통과를 구분한다.

## 남은 전체 과제

1. 이번 변경의 운영 병합/배포. `schema.sql`의 actor_id/record_id는 추가 컬럼이며 운영에서는 아직 실행하지 않는다. 기존 워커를 종료하고 새 워커만 실행한다.
2. 평가→보상→급여 및 경비→전표의 모든 역할·마감·반려 조합을 실제 UI/API 연속 시나리오로 확대. 이번 브라우저 신규 검증은 복구 흐름이며 모든 업무 QA 완료를 의미하지 않는다.
3. 이력 민감값의 중첩 검사, 보관/내보내기/삭제 미리보기. 이번 트랜잭션 보장은 record_revisions 대상이며 JSON employee_history 등 다른 감사 저장소 전체를 통합한 것은 아니다.
4. 교육 원장의 공통 과정 ID와 관리자 확인/연결 해제 화면. 동일 이름을 근거로 자동 병합하지 않는다.
5. 권한·도메인 코드의 점진적 분리, Action 실행환경 업그레이드. 대규모 재작성/운영 자료 자동 삭제는 하지 않는다.

파일 모드는 단일 서버 프로세스 전제다. 여러 프로세스가 같은 JSON 파일을 공유하는 운영 방식까지 지원한다고 해석하면 안 된다. 파일 디스크 자체 유실/소실에 대비한 별도 백업도 계속 필요하다.

# ERP 기준정보 동시 편집 보호 — 2026-11-20

## 동작

품목, 창고/위치, 영업목표의 POST 저장은 기존 레코드의 `_rev`를 비교한다. 먼저 성공한 저장만 반영하고, 같은 이전 버전을 사용한 두 번째 저장은 HTTP 409 `ERP_MASTER_CONFLICT`로 거부한다. `restore:true`도 살아 있는 자료의 버전 검사를 건너뛰지 못한다. JSON은 검사와 원자적 파일 저장 사이에 비동기 작업을 두지 않으며 PostgreSQL은 `ON CONFLICT DO UPDATE ... WHERE`의 행 잠금 안에서 비교한다.

품목/창고 편집 화면은 열었을 때의 버전을 입력 폼에 보관한다. 목록이 뒤에서 새로 고쳐져도 편집 버전은 바뀌지 않는다. 충돌 시 **입력 유지** 또는 **최신 내용 불러오기**를 선택한다. 최신 자료를 불러오는 것은 현재 입력을 교체하는 명시적 동작이며 자동 재저장/덮어쓰기를 하지 않는다.

## API 계약

- 신규 생성: `_rev`를 보내지 않는다. 같은 ID가 이미 있으면 덮어쓰지 않고 409를 반환한다.
- 기존 수정: 조회/저장 응답의 `_rev`를 그대로 보낸다. 성공 응답에는 새 UUID 버전이 포함된다.
- 버전 없는 예전 레코드: 조회 결과에 `_rev`가 없을 때만 `_rev: "legacy"`를 보낸다. 첫 수정부터 UUID 버전으로 전환한다. 전체 DB 마이그레이션은 필요 없다.
- `_rev`가 있는 요청의 ID가 존재하지 않으면 새 자료로 생성하지 않는다.
- 잘못된 타입/형식은 400 `ERP_MASTER_REVISION_INVALID`, 오래된/누락된 버전은 409다. 기존 외부 연동의 무조건 upsert는 수정이 필요하다.
- 삭제 표식이 있는 자료는 기존처럼 명시적 복원 확인을 요구한다. 복원 후에는 새 버전을 발급한다.

## 검증

JSON/임시 PostgreSQL 공통 회귀 테스트에 동시 저장의 단일 성공, 원본 보존, 누락/잘못된 버전, 복원 옵션 우회 차단, 복원 전 버전 재사용 차단을 포함한다. 별도로 예전 버전 없는 레코드와 파일 저장 실패 후 같은 버전으로 재시도를 검증한다. 브라우저 테스트는 충돌 입력 보존, 명시적 새로 읽기, 재편집 저장, 목록 캐시 갱신 시 편집 버전 유지와 기존 삭제 복원 흐름을 확인한다.

## 남은 범위

2026-11-23 보완으로 편집 저장과 삭제 요청 모두 revision 조건을 적용한다. 회사 미지정(NULL) 자료의 소유권 정책, 회계 전표·세금계산서 금액 대사는 별도다. 운영 데이터의 자동 귀속·삭제·금액 수정은 수행하지 않는다. 영업목표 UI는 현재 신규 등록/삭제만 제공하며, 수정 API에는 동일한 버전 검사가 적용된다.

## 2026-11-23 삭제 충돌 및 영향 범위 확인

품목·창고·영업목표 삭제 요청에도 조회한 자료의 `_rev`가 필요하다. 살아 있는 자료에 버전이 없거나 오래된 버전이면 409를 반환하고 삭제하지 않는다. 이미 삭제됐거나 현재 회사에 없는 자료는 원본을 바꾸지 않고 성공으로 응답한다. 복원한 자료에는 새 버전이 있으므로 복원 전 삭제 요청을 재전송해도 다시 삭제되지 않는다. 예전 버전 없는 자료는 `legacy`로 삭제한다.

화면은 삭제 확인창을 열 때의 버전을 고정한다. 확인 중 다른 사용자가 수정하면 최신 목록을 불러오고 다시 확인하도록 안내하며 자동으로 삭제를 재시도하지 않는다. 영업목표 확인창은 대시보드의 `targetsByYear`를 사용해 담당자·기간·목표 금액을 표시한다. 대시보드 응답에는 이를 위한 연도와 버전이 포함된다.

JSON 원자적 저장과 PostgreSQL 행 잠금 안에서 버전/참조 검사를 수행한다. 영업목표도 같은 삭제 함수로 통합한다. 회귀 검증은 편집-삭제 동시 요청의 단일 성공, 삭제 재시도, 복원 후 오래된 삭제 차단, 참조 생성과 삭제 경합, 저장 실패 후 재시도를 포함한다. 브라우저 검증은 확인 중 변경된 자료 보호와 최신 영향 범위의 재확인을 검사한다.

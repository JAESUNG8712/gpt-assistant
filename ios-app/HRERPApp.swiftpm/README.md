# 인사 ERP 앱 (Swift Playgrounds)

이 저장소의 HR/ERP 백엔드(`server.js`, 루트)에 연결하는 SwiftUI 클라이언트입니다.
AI 어시스턴트(`ai/main.py`)를 연동하는 `../GPTAssistant.swiftpm`과는 완전히 별개의 앱입니다
(백엔드가 다르고, 인증 방식도 다릅니다).

## 배경

`docs/API_CONTRACT.md`(`claude/mobile-hr-app-testing-rDc2F` 브랜치)에 따르면 `server.js`는
로그인/전자결재/근태/경비청구/채용/회계/영업/재고/PMS 등을 아우르는 **100개 이상의
엔드포인트**를 가진 실제 운영 중인 인사·ERP 시스템입니다(`HANDOFF.md` 기준 실직원 256명
데이터 운영 중). `public/index.html` 자체가 2만 줄이 넘는 SPA라, 네이티브 앱으로 전체
쓰기(CRUD) 기능까지 1:1로 재구현하는 것은 여전히 이번 범위를 벗어납니다. 대신:

- 인증(로그인 + Bearer 토큰) + "클라이언트 신뢰형 전체 상태 블롭"(`GET /data` / `POST /save`)
  아키텍처를 구현하고, 그 블롭에서 가장 자주 쓰이는 4개 컬렉션(직원·근태·전자결재·경비청구)에
  실제 쓰기 가능한 화면을 만들었습니다.
- 회계·영업/재고·PMS·채용은 서버가 전용 REST 테이블로 관리하는 **독립 리소스**라, 조회
  중심(+ PMS 투입률은 입력까지)으로 화면을 추가해 커버리지를 크게 넓혔습니다. 자세한 내용은
  아래 "구현된 기능" 표 참고.

## 디자인

실제 웹 앱(`public/index.html`)과 동일한 디자인 언어를 그대로 옮겼습니다 — 배경 `#f1f5f9`,
흰색 카드 + 옅은 테두리(`#e2e8f0`), 포인트 컬러 `#2563eb`. 기본 다크 `List`/`Form` 대신
`Theme.swift`의 `AppCard`/`StatTile`/`ModuleCard`/`StatusPill` 등 공용 컴포넌트로 통일했고,
시스템 다크모드와 무관하게 항상 라이트 테마로 고정됩니다(`.preferredColorScheme(.light)`) —
웹 앱 자체가 라이트 전용이라 다크모드 지원이 의미가 없기 때문입니다.

### 화면 크기에 따른 레이아웃 전환

`RootView`가 `horizontalSizeClass`를 보고 레이아웃을 고릅니다 — 웹 앱의 좌측 사이드바와
동일한 경험을 주기 위함입니다.

- **좁은 화면(iPhone, 작은 Split View 등, compact)**: `MainTabView` — 하단 탭바 + "더보기" 허브
- **넓은 화면(iPad 가로, 창을 크게 늘린 경우, regular)**: `SidebarRootView` —
  `NavigationSplitView` 기반 좌측 사이드바(전체 12개 섹션이 허브 그룹 없이 평평하게 나열됨) +
  우측 상세 2단 구성

두 레이아웃 모두 같은 `HRDataStore` 인스턴스를 각자 소유하고(레이아웃 전환 시 재로드),
같은 화면 컴포넌트(`DashboardView`, `AttendanceView` 등)를 그대로 재사용합니다 — 각 화면은
자기 자신의 `NavigationStack`을 갖지 않고, 상위(탭 또는 사이드바)가 제공하는 `NavigationStack`
안에서 표시됩니다.

### 탐색 상태 리셋

탭을 벗어났다가 돌아오면(또는 사이드바에서 다른 섹션을 고르면) 그 탭/섹션의 `NavigationStack`을
루트 화면부터 다시 보이도록 강제 리셋합니다. 이렇게 하지 않으면 예를 들어 "더보기 → 조직도 →
직원 상세"까지 들어간 뒤 다른 탭에 갔다가 다시 "더보기"로 돌아왔을 때 직원 상세 화면이 그대로
남아있어서, 원래 보려던 "더보기" 목록을 보려면 뒤로가기를 한 번 더 눌러야 하는 문제가
있었습니다.

처음엔 `NavigationStack(path:)` + 빈 `NavigationPath()`로 리셋을 시도했지만, QA 결과 이
방식이 실제로는 아무 효과가 없다는 걸 확인했습니다 — 이 앱의 모든 화면 전환이
`NavigationLink(value:)` + `.navigationDestination(for:)`(Hashable 값 기반, `NavigationPath`가
추적하는 방식)가 아니라 옛 방식인 `NavigationLink { View } label: { ... }`(뷰 빌더 방식)를
쓰고 있어서, push가 일어나도 `NavigationPath`엔 아무것도 기록되지 않기 때문입니다. 그래서 각
탭/사이드바 상세 영역의 `NavigationStack` 자체에 `.id()`를 걸어, 화면을 벗어나는 순간 id를
바꿔 그 `NavigationStack`을 통째로 새로 만드는 방식으로 교체했습니다 — push 방식과 무관하게
항상 확실히 리셋됩니다(`MainTabView`의 `onChange(of: selectedTab)`,
`SidebarRootView`의 `onChange(of: selection)`).

## 왜 전체 상태를 딕셔너리로 다루는가 (근태·전자결재·경비청구·직원)

`GET /data`는 `employees`, `kpiEntries`, `settings`, `orgDB`, `coreTalentPool` 등
**30개 이상의 필드**를 가진 하나의 큰 JSON을 반환하고, `POST /save`는 그 전체를 통째로
다시 업로드하는 구조입니다(`lib/collections.js`의 `ID_KEYED_LIST_FIELDS`/`SINGLETON_FIELDS`
참고). 이 앱이 이해하지 못하는 필드까지 정적 Swift 구조체로 디코드했다가 다시 인코드해서
되돌리면, 구조체에 없는 필드가 저장 과정에서 통째로 사라집니다(실제 서비스 데이터 유실).

그래서 `HRDataStore`는 전체 블롭을 `[String: Any]`로만 들고 있다가, 변경이 필요한 부분만
(예: 근태 레코드 하나, 결재 문서의 결재자 상태 하나) 직접 딕셔너리 키를 수정하고, 나머지는
손대지 않은 채 그대로 다시 `POST /save`로 돌려보냅니다. 표시용으로만 쓰는 타입(`Employee`,
`AttendanceRecord`, `ApprovalDocSummary`, `ExpenseClaim`)은 읽기 전용 `Decodable`이며
저장 경로에는 관여하지 않습니다.

반면 회계/영업재고/PMS/채용(`/api/accounting/*`, `/api/erp/*`, `/api/pms/*`,
`/api/recruit/*`)은 서버가 각자 전용 테이블로 직접 관리하는 독립 리소스라 이 유실 위험이
없습니다 — 그래서 `ModuleModels.swift`의 모델들은 평범한 `Decodable` 구조체입니다.

## 구현된 기능

| 탭 | 화면 | 내용 |
|---|---|---|
| 홈 | 대시보드 | 내 정보, 오늘 근태 상태 + 출근/퇴근 체크, 결재·경비청구·직원수·KPI 건수 요약, 전체 섹션 바로가기 그리드 |
| 근태 | 내 근태 | 내 근태 이력 전체 |
| 전자결재 | 결재함 | 내가 결재할 문서 / 내가 상신한 문서, 결재선 확인, 승인·반려, **신규 상신**(제목·내용·결재자 다중 선택) |
| 경비청구 | 청구 목록 | 내 청구 목록, 신규 작성(항목별 금액/분류/메모), 대기 건 회수 |
| 더보기 → 알림 | 인앱 알림 피드 | 내가 처리할 결재 / 대기중인 내 경비청구 / 안전재고 미만 품목을 한 화면에 모아 보여줌 |
| 더보기 → 조직도 | 직원 검색 + 상세 | 전 직원 검색(이름/부서/팀), 탭하면 사번·연락처·입사일 등 상세 정보(급여 제외). **관리자(`role=="admin"`)는 추가로**: 목록에 퇴사자도 표시 + **신규 직원 등록**(＋ 버튼), 상세 화면에서 **정보 수정**(부서/팀/역할/직급/직책/연봉/연락처)·**퇴직 처리**(퇴직일·사유 등록, 로그인 차단, 대기중인 경비청구 자동 반려) |
| 더보기 → 회계 | 계정과목 · 전표 | 목록 조회 (차대변 라인·거래처·상태 포함) — 읽기 전용 |
| 더보기 → 영업/재고 | 품목 · 견적서 · 발주서 · 재고현황 | 목록 조회 (품목명·창고명 매핑 포함) — 읽기 전용 |
| 더보기 → PMS | 프로젝트 · 투입률 | 프로젝트 목록 조회 + **내 투입률 직접 입력**(월별 100% 초과 시 서버가 거부) |
| 더보기 → 채용 | 공고 · 지원자 | 목록 조회 + 지원자 이름/이메일 검색 — 읽기 전용 |
| 더보기 → 평가/KPI | 내 목표·점수 | 자기/1차/2차/최종 점수 조회 — 읽기 전용 |
| 설정 | 계정/서버 | 로그인 계정 정보, 서버 URL, `GET /status` 연결 확인, 로그아웃 |

넓은 화면(사이드바 모드)에서는 "더보기" 그룹 없이 위 12개 섹션이 좌측에 모두 평평하게 나열됩니다.

### 알림 관련 주의

실제 푸시 알림(APNs) 인프라는 없습니다 — `server.js`에 그런 엔드포인트 자체가 없기
때문입니다. "알림" 화면은 이미 갖고 있는 데이터에서 "지금 확인해야 할 것"을 모아 보여주는
인앱 피드이며, 새로고침해야 갱신됩니다(실시간 아님). `tieNotifications`(평가 동점자 처리
알림)이나 `integrationLogs` 같은 서버 쪽 다른 알림성 컬렉션은 아직 반영하지 않았습니다.

### 평가/KPI 관련 주의

`kpiEntries`는 목표 설정 → 자기평가 → 1차평가 → 2차평가 → 최종확정으로 이어지는 다면평가
워크플로 전체를 담는 컬렉션입니다. 이번 앱은 이미 입력되어 있는 값을 읽기 전용으로 보여주기만
합니다 — 목표 신규 작성, 점수 입력·수정, 동점자 처리, 등급 조정/승진 등은 모두 범위 밖입니다.

로그인: `POST /login` — 아이디/비밀번호(+2단계 인증 코드), 토큰은 UserDefaults가 아닌
**Keychain**에 저장됩니다.

### 전자결재 승인/반려 로직 관련 주의

`public/index.html`의 `approveApprovalDoc()`/`rejectApprovalDoc()` 로직(결재자
`waiting`→`pending` 순차 진행, 전원 승인 시 문서 `approved`)을 그대로 옮겼습니다. 다만
템플릿별 부가 효과(예: 근태 신청 승인 시 근태 레코드 자동 반영, 거래처 등록 신청 승인 시
거래처 자동 생성)는 `_applyAttendanceApproval()`/`_autoRegisterVendorFromApproval()` 등
`index.html`에만 있는 로직이라 이번 앱에는 옮기지 않았습니다 — 그런 특수 템플릿 문서를
이 앱으로 승인하면 결재선 상태는 정상 반영되지만 부가 효과는 발생하지 않습니다.

### 전자결재 신규 상신 관련 주의

`approvalDocs`는 GET /data 블롭의 일부라 전용 REST 엔드포인트가 없습니다 — 웹 앱도
클라이언트에서 문서를 만들어 `approvalDocs` 배열에 추가한 뒤 그대로 `POST /save`로
올리는 방식입니다. 이 앱은 그중 **"일반 결재"(`tpl-general`: 제목+내용)** 템플릿 형태로만
상신을 지원합니다. 휴가·경조사·출장 등 나머지 12개 빌트인 템플릿(`tpl-vacation` 등)과
사용자 정의 템플릿은 `approvalTemplates` 컬렉션에서 필드 목록을 읽어와 동적 폼을 그려야
하는 별도 작업이 필요해 범위 밖으로 뒀습니다.

## 사용 방법

1. `server.js`를 배포합니다(배포 브랜치 `claude/mobile-hr-app-testing-rDc2F`).
2. Swift Playgrounds에서 `ios-app/HRERPApp.swiftpm`을 엽니다 — 서버 주소는 더 이상
   기본값으로 채워져 있지 않습니다(멀티테넌트 전환 전까지, 앱을 배포해도 실제 운영
   서버로 자동 접속되지 않도록 의도적으로 비워둠). 로그인 화면의 "서버 설정"에서
   배포한 서버 주소를 직접 입력해야 합니다.
3. 로그인 화면에서 실제 계정(웹에서 쓰던 아이디/비밀번호)으로 로그인합니다.
   `HANDOFF.md`에 적힌 시드 데이터 예시 계정은 이후 실사용 중 비밀번호가 바뀌었을 수 있어
   보장되지 않습니다.
4. 로그인 후 하단 탭에서 홈/근태/전자결재/경비청구/더보기/설정을 확인합니다.

## 알려진 한계 (클라이언트에서 고칠 수 없는 서버 쪽 제약)

100명 이상 동시 접속·계정 간 데이터 격리를 실제 운영 서버(프로덕션, 실직원 데이터) 대상으로
실측 부하 테스트한 결과 발견된 항목입니다. 전부 `server.js`(이 앱이 통신하는 배포 브랜치
`claude/mobile-hr-app-testing-rDc2F`) 쪽 수정이 필요해 이 iOS 앱만으로는 고칠 수 없습니다.
(이전 버전 문서에 있던 "tombstone을 대부분 지원하지 않는다"는 서술은 부정확했음을 이번에
확인해서 정정합니다 — `recordTombstones`는 이미 대부분의 id-키 컬렉션에 일반화되어 있고,
이 앱의 `HRDataStore.withdrawExpenseClaim`도 이번에 그걸 쓰도록 고쳤습니다. 아래는 그와
별개로 실측으로 새로 확인된, 여전히 서버 쪽에 남아있는 문제입니다.)

- **[중요] `employees` 컬렉션은 삭제 자체가 아예 반영되지 않음(Postgres 모드)**: 다른
  컬렉션과 달리 `employees`/`kpiEntries`는 전용 테이블이라 `POST /save`의 처리 로직이
  다른데, 이 전용 경로는 들어온 배열에 대해 INSERT/UPDATE만 수행하고 `recordTombstones`나
  "배열에서 빠진 id"를 전혀 확인하지 않습니다 — 그래서 클라이언트가 직원을 배열에서 지우고
  tombstone까지 정확히 넣어 저장해도 실제로는 아무 효과가 없고, DB에는 그 직원이 계속
  남습니다(직접 확인: 테스트 계정 삭제 시도가 `ok:true`로 성공 응답했지만 재조회 시 그대로
  남아있었음 — 대신 `active:false`로 비활성화하는 방식으로 우회 처리함). 유일한 하드
  삭제 경로는 `POST /restore`(스냅샷 복원, `deleteExtras:true`)뿐인데 이건 지정한 필드
  전체를 옛 스냅샷 값으로 되돌리는 훨씬 파괴적인 관리자 기능이라 직원 1~2명 정리 용도로
  쓰기엔 부적합합니다.
- **[중요] 전자결재 동시 승인/반려 시 한쪽 결정이 조용히 유실됨**: 두 결재자가 같은 문서를
  진짜 동시에(같은 버전에서 시작해) 각각 승인/반려하면, `smartMerge`가 문서 레코드 전체를
  `updatedAt` 기준 승자독식으로 병합할 뿐 `approvers` 배열 내부까지 들여다보며 병합하지
  않습니다. 실측 결과 한쪽 결정(반려)이 완전히 사라지고 응답은 두 요청 모두 `ok:true`였습니다
  — 사용자가 유실을 알아챌 방법이 없습니다. 근본 수정은 서버가 `approvalDocs`도 `approvers`
  하위 배열 단위로 병합하도록 `smartMerge`를 확장해야 합니다.
- **[심각] `POST /save`가 경비청구의 소유자(empId)를 검증하지 않음**: 실측 결과 qa_test_2
  계정 토큰으로 qa_test_1이 만든 pending 경비청구를 배열에서 지워 저장하면 서버가 그대로
  받아들였습니다(`200 {"ok":true}`). 이 앱 UI는 본인 것만 회수 버튼을 보여줘 정상 사용
  경로에서는 막히지만, API를 직접 호출하면 누구나 남의 pending 경비청구를 지울 수 있는
  상태입니다 — 서버가 삭제되는 레코드의 empId와 요청자 empId(관리자 제외)를 대조하는
  검증을 추가해야 합니다.
- **[경미] `approvalDocs`에 스키마 검증이 없음**: `approvers:[]`(결재자 0명)인 문서도
  `POST /save`가 그대로 받아들여, 영원히 대기 상태로 남는 고아 문서가 만들어질 수 있습니다.
  이 앱 UI는 결재자가 0명이면 상신 버튼 자체를 비활성화해 정상 사용 경로에서는 발생하지
  않습니다. 자기 자신을 결재자로 지정해 스스로 승인하는 것도 서버가 막지 않습니다(직무분리
  미검증) — 둘 다 서버 쪽 검증 추가가 필요합니다.
- **[참고] 동시 접속 부하**: GET /data를 100~200개 동시 연결로 실측한 결과 90~97.5% 성공,
  응답 지연시간이 평균 6.5~18.6초까지 늘어났고 나머지는 Postgres 커넥션 풀 타임아웃(500)이었습니다
  (서버가 죽거나 데이터가 깨지지는 않음). Render 무료 티어 기준으로는 100명 이상 동시 접속
  시 사용성 저하가 실제로 체감될 수준입니다 — 유료 플랜 전환 또는 커넥션 풀 크기 조정을
  고려할 만합니다.
- **[해결됨, 참고용] id 충돌**: 클라이언트가 만드는 새 경비청구/전자결재 문서 id가 순수
  밀리초 타임스탬프였을 때, 두 기기가 정확히 같은 밀리초에 저장하면 하나가 조용히 사라지는
  것을 실측으로 재현했습니다(`mergeArrayById`가 id 단위로만 승자독식). 이 앱은 `Models.swift`의
  `newClientRecordId()`로 끝에 무작위 3자리를 더해 충돌 확률을 대폭 낮췄지만, `employees`
  전용의 `POST /api/employees/next-id` 같은 서버 발급 원자적 id가 아니라 여전히 이론상
  충돌 가능성은 남아있습니다.

## 이번 QA 라운드에서 고친 것

기능별 에이전트로 실데이터 조회/조작, 다중 접속 시나리오를 점검해 아래 항목을 고쳤습니다.

- [치명적] 위 "탐색 상태 리셋" 항목 — `NavigationPath` 리셋이 실제로는 무효였던 걸
  `.id()` 강제 재생성 방식으로 교체(탭바·사이드바 양쪽 모두).
- 토큰 만료(401) 시 회계/영업재고/PMS/채용/알림 5개 화면이 "세션 만료"로 안내하며 로그인
  화면으로 돌아가는 대신 일반 오류 메시지만 보여주던 것을 `HRDataStore`와 동일하게
  `session.handleUnauthorized()`를 호출하도록 통일.
  회계/영업재고/PMS/채용은 `HRDataStore`의 블롭 컬렉션과 달리 독립 REST 엔드포인트를 쓰기
  때문에 각자 401을 직접 확인해야 했습니다.
- `APIClient.decodeList`(회계/영업재고/PMS/채용 REST 목록 조회)가 배열 전체를 한 번에
  디코드해 레코드 하나만 예상과 다른 형태여도 목록 전체가 실패하던 것을, `HRDataStore`가 이미
  쓰던 것과 같은 레코드 단위 디코드로 교체 — 문제 있는 레코드만 건너뛰고 나머지는 정상 표시.
- PMS 투입률 입력 시 프로젝트 선택 목록에 내가 멤버가 아닌 프로젝트까지 나와 실수로 잘못된
  프로젝트에 입력하기 쉬웠던 것을, 내가 멤버로 등록된 프로젝트(+ 멤버 제한이 없는 프로젝트)로
  좁힘. 관리자(`role == "admin"`) 계정은 기존처럼 전체 프로젝트를 봅니다.
- Keychain 저장/삭제 API(`SecItemAdd`/`SecItemDelete`)의 실패 여부(OSStatus)를 무시하던 것을
  확인하도록 수정, 접근성 수준을 `kSecAttrAccessibleAfterFirstUnlock`에서
  `...ThisDeviceOnly`로 변경해 로그인 토큰이 iCloud Keychain 백업/동기화 대상에 포함되지
  않도록 함.

### 2차 QA 라운드(실제 운영 서버 대상 실측 부하·격리 테스트) 이후 추가로 고친 것

전용 테스트 계정 2개를 새로 발급해 프로덕션 서버에 실제 100~200개 동시 연결 부하 테스트,
계정 간 데이터 격리 테스트, 기능별 반복 회귀 테스트, 코드 레벨 클라이언트 정합성 감사를
진행(테스트로 만든 데이터는 전부 정리, 테스트 계정 2개는 비활성화 처리함 — 위 "알려진
한계"의 employees 삭제 미반영 문제로 완전 삭제는 불가해 `active:false`로 비활성화).

- `HRDataStore.withdrawExpenseClaim`이 배열에서 레코드를 지우기만 하고 `recordTombstones`를
  남기지 않던 것을 수정 — 실제 서버 소스(`server.js`)를 확인해보니 웹 앱은 삭제 시 반드시
  `_tombstone("expenseClaims", id)`를 같이 호출하고 있었고, 그러지 않으면 회수 직후 다른
  클라이언트의 저장과 버전 충돌이 났을 때 회수한 청구가 되살아날 수 있는 상태였음.
- 새 경비청구/전자결재 문서의 id를 `Int(Date().timeIntervalSince1970*1000)`(순수 밀리초
  타임스탬프)로만 만들던 것이, 부하 테스트로 "두 기기가 같은 밀리초에 저장하면 하나가
  조용히 사라진다"는 걸 실제로 재현시켜 확인됨 — `Models.swift`에 `newClientRecordId()`를
  추가해 끝에 무작위 3자리를 더하는 방식으로 충돌 확률을 대폭 낮춤.
- `HRDataStore.reload()`/`save()`가 겹쳐서 호출되면(예: 근태 체크 직후 다른 화면에서 결재
  승인) 두 저장 응답이 도착 순서대로 반영되면서 나중 응답이 최신 상태를 덮어쓸 수 있던 것을,
  `isLoading` 재진입 가드로 겹치는 호출은 조용히 건너뛰도록 수정.
- `PMSView`의 투입률 저장(`NewAllocationView.save()`)이 다른 쓰기 경로와 달리 401 처리가
  빠져있던 것을 통일.

## 관리자 전용: 직원 관리 (신규 등록 / 정보 수정 / 퇴직 처리)

사용자 요청에 따라 웹 관리자 화면과 동일한 수준의 직원 관리 쓰기 권한을 `role=="admin"`
계정에 부여했습니다(`EmployeeDirectoryView`/`EmployeeDetailView` 참고, 로직은
`index.html`의 `submitHRForm()`/`submitHRChange()`/`submitRetire()`를 그대로 옮김).

- **신규 등록**: 조직도 화면 우측 상단 ＋ 버튼(관리자에게만 보임) → 이름/사번/부서(+팀,
  임원 제외 필수)/입사일 등 필수 항목과 로그인ID·비밀번호(미입력 시 사번으로 자동 채움)·
  연봉·연락처·학력 등을 입력해 등록. id는 반드시 서버 원자적 발급
  (`POST /api/employees/next-id`)으로 받아 여러 관리자가 동시에 등록해도 충돌하지 않습니다
  (근거: 서버 소스 주석에 남아있는 실측 기록 — 이 엔드포인트가 생기기 전엔 30명 동시 등록 시
  27명이 유실됐음). 사번·로그인ID 중복은 클라이언트에서 먼저 막습니다.
- **정보 수정**: 직원 상세 화면의 `···` 메뉴 → "정보 수정" — 부서/팀/역할/직군/직급/직급연차/
  직책/연봉/연락처를 즉시 수정하고, 바뀐 필드만 모아 `hrHistory`에 감사 기록을 한 건
  남깁니다. 이름/사번/로그인ID/비밀번호는 이 화면에서 바꿀 수 없습니다(로그인ID 변경은
  중복 검증이 더 까다롭고, 비밀번호 재설정은 별도 확인 절차가 있는 게 안전하다고 판단해
  범위 밖으로 뒀습니다).
- **퇴직 처리**: 같은 메뉴의 "퇴직 처리"(재직자에게만 표시) — 퇴직일·사유·비고를 입력하면
  `active:false`+`retireDate`/`retireReason`이 반영되어 즉시 로그인이 막히고, 그 직원의
  **대기중인 경비청구는 자동 반려**됩니다(웹 앱의 `_cleanupRetiredEmpReferences()`와 동일).
  이 앱이 다루지 않는 `approvalDelegations`/`overtimeRequests` 컬렉션의 정리는 하지 않습니다.
- **완전 삭제는 지원하지 않습니다** — 위 "알려진 한계"에 적은 대로 `employees` 컬렉션은
  Postgres 모드에서 배열 삭제/tombstone이 전혀 반영되지 않는 서버 쪽 버그가 있어, 퇴직
  처리(비활성화)만 안전하게 동작합니다. 실제로 만든 QA 테스트 계정 3개(qa_test_1/2,
  qa_smoke_1)로 신규 등록→수정→퇴직 처리 전 과정을 프로덕션 서버에 직접 실행해 검증했습니다.

## 범위 밖 (다음 단계 후보)

- 회계·영업재고·채용은 **조회 전용**입니다 — 계정과목/전표 등록, 견적서/발주서 작성,
  채용공고 등록 등 쓰기 기능은 아직 없습니다(각 엔드포인트에 대응하는 POST 메서드를
  `APIClient`에 추가하고 입력 폼만 만들면 되는 구조라, 확장은 이어서 가능).
- 직원 관리(신규 등록/정보 수정/퇴직 처리)는 관리자 전용으로 구현됨(아래 "관리자 전용:
  직원 관리" 참고) — 단, 로그인ID·비밀번호 변경, "발령·변동 이력"의 유형별 전용 폼(전보·
  승진·휴직 등)과 미래 날짜 예약 적용, 완전 삭제(하드 삭제)는 범위 밖.
- KPI/평가는 조회 전용(목표 작성, 점수 입력, 동점자 처리, 등급조정/승진 등은 범위 밖).
- 전자결재 신규 상신은 "일반 결재"(제목+내용) 템플릿만 지원 — 휴가·경조사·출장 등 나머지
  템플릿별 동적 폼은 범위 밖.
- 2FA 최초 등록 플로우(`/api/auth/2fa/generate-secret`) — 로그인 시 이미 등록된 계정의
  코드 입력만 지원, 신규 등록 화면은 없음.
- 실시간 동기화(`GET /events`, SSE) — 지금은 pull-to-refresh로만 최신화합니다. 진짜 푸시
  알림(APNs)도 없습니다.
- 게시판(`boardPosts`), 예약(`roomReservations`), 자격증(`certRequests`), 복지포인트
  (`welfarePoints`) 등 `lib/collections.js`에 있는 나머지 컬렉션들은 화면 자체가 없습니다.
